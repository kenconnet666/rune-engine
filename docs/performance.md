# 性能预算

“预算”是一条线：量出来超过它，就当成出了问题来查，而不是等到有人觉得卡。线都定在现状上面留出余量的地方——
正常加功能碰不到，不小心做错了事（把一个大依赖打进包里、在每天都跑的循环里加了一次全表扫描）会碰到。

数是 2026-11-14 在开发机上量的（Windows 11，桌面显卡，Chrome 稳定版）；CI 的机器慢一些，线里已经算上了。

## 自动核对的

| 量什么                                                   | 现状       | 线      | 在哪里核对                  |
| -------------------------------------------------------- | ---------- | ------- | --------------------------- |
| 页面的脚本和样式（gzip）                                 | 139 KB     | 180 KB  | `pnpm check:budget`         |
| 主机线程（模拟）的脚本（gzip）                           | 25 KB      | 32 KB   | 同上                        |
| 渲染线程的脚本（gzip）                                   | 41 KB      | 48 KB   | 同上                        |
| 粗的地图网格（gzip）                                     | 114 KB     | 150 KB  | 同上                        |
| **打开页面要下的合计**（gzip）                           | 320 KB     | 400 KB  | 同上                        |
| 细的地图网格（gzip，画面出来以后后台加载）               | 1052 KB    | 1300 KB | 同上                        |
| 模拟一天（两方电脑各想一次、各看一次、走一步），CPU 时间 | 约 2 ms    | 10 ms   | `client/src/budget.test.ts` |
| 经网络发的一份状态                                       | 约 12.7 KB | 16 KB   | 同上                        |
| 一局的记录（JSON；存档、云存档放的就是它）               | 约 80 KB   | 256 KB  | 同上                        |

`pnpm check:budget` 读构建产物（`games/miwang/client/dist`），CI 的冒烟测试那一步在构建之后跑它；
预算表里没列到的新文件也会让它不过——新冒出来的东西要有人看一眼，决定它算哪一类。
`budget.test.ts` 跟着 `pnpm test` 跑。

线为什么是这些数：

- **打开页面 400 KB**：一般的家用网络一两秒下完，手机网络三四秒。细的网格不在里面——先用粗的把画面画出来，细的在后台拿。
- **模拟一天 10 毫秒**：10 倍速时主机每 40 毫秒要走一天，10 毫秒让它只占一个核的四分之一；联机时主机还要给两边各出一份视图。
  单独量大约 2 毫秒；测试并行跑的时候同样的活会量出两三倍（抢核、垃圾回收），所以线没有贴着现状定。
- **一份状态 16 KB**：联机走中转时每秒大约发八份，16 KB 就是每秒 128 KB 的上行，再多一般的家用上行就吃紧了。
- **一局的记录 256 KB**：云存档一份的上限是压缩后 512 KB，记录压缩后大约是原来的四分之一，离上限很远；
  超过 256 KB 多半是有命令在被成批地重复记录。

## 手动核对的

画面流不流畅要在真的显卡上量，CI 的机器没有显卡（用的是软件渲染），量出来的数不作数。改了渲染、界面里每帧都跑的东西之后在本机跑：

```bash
pnpm dev
pnpm perf            # 另一个终端；量三段，各几秒：1 倍速、10 倍速、10 倍速并放大
pnpm perf --budget   # 同上，超了线以 1 退出
```

| 量什么                                                | 现状      | 线          |
| ----------------------------------------------------- | --------- | ----------- |
| 主线程被卡住的时间，95% 的情况（10 倍速）             | 约 3 ms   | 20 ms       |
| 长帧（超过 50 ms 的帧），稳定打着的时候，几秒的测量里 | 0 个      | 不超过 2 个 |
| 渲染线程每帧在自己这头花的时间（平均）                | 约 0.2 ms | 4 ms        |

量的时候画布是 3840×1854（两倍像素密度）、4 倍多重采样；放大那一段用的是 9 万个顶点的细节网格。

- **主线程 20 毫秒**：界面的按下、悬停要在一两帧里有反应。主线程上没有模拟也没有渲染（各在一个 Worker 里），卡顿只可能来自界面自己的重画。
- **渲染线程 4 毫秒**：一帧 16.7 毫秒，给合成、给显卡留足余地；地图上的东西再多几倍也还在里面。

- **界面不是每一份状态都跟**：主机每走一天发来一份状态，10 倍速时一秒二十多份。每跟一次，整套面板就要重新排版、
  绘制一遍（十几到二十几毫秒）——脚本本身很少，时间花在浏览器自己的渲染上。界面两次之间至少隔 100 毫秒
  （`session/core.ts` 的 `VIEW_GAP_MS`），中间来的只留最新的一份；下了命令、暂停、分出胜负这些马上换。
  不这样做的话，面板一多这个数就到线上（玩法加到五项时量到过 14 到 34 毫秒）。地图不受影响，它在渲染线程里另有一路数据。
- **界面是画进画布的**（见 `interface.md`）：重拍一层界面就是把一整层重新画一遍，拍得太勤，帧就开始等合成
  （主线程没被卡住，长帧却一个接一个）。采集按“每秒重画多少像素”讲节奏，上面那条长帧的线就是它守着的；
  改了采集的节奏、往界面里加了一直在动的东西之后要重新量。拿不准一个数是不是无界面模式带来的，加 `--headed` 在真窗口里对一下。

帧率本身不设线：无界面的浏览器里它跟着机器当时的负载走，只能当参考。
开局那一下（关对话框、起主机、画第一帧）会有两三个长帧，最长一两百毫秒，是一次性的，不在上面那条线里：
脚本等开局过去两三秒才开始量。

## 没有设线的

- **内存**：一局打下来 JS 堆在几十 MB，没有看到随时间涨的迹象，没有专门量过长时间挂机。
- **冷启动的时间**（打开页面到主菜单出来）：软件渲染的 CI 上是十几秒，真机上不到一秒，中间差的是显卡初始化，不是能靠代码省下来的。
- **手机**：只在模拟的视口里核对过布局，没有在真机上量过性能。
